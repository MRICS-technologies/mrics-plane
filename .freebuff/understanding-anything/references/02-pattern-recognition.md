# Pattern Recognition & Analogy Mapping

The second toolkit. Once a topic has a rough structure, the way to deepen understanding is to connect it to things the user already knows. The brain understands by analogy, not by raw new data.

## Analogical Reasoning (Structure Mapping)

When the user meets something unfamiliar, ask: "What is this like? Have I seen something with the same shape before?"

**Why it works.** A good analogy carries over a known set of relationships to a new domain, letting the user transfer understanding instead of starting from scratch. It works by matching *structural* similarities — if two things share an underlying structure or dynamic, understanding one gives you hypotheses about the other.

**How to apply with the user.**
- Once the structure is rough, ask: "Does this remind you of anything? Any system you already understand that works similarly?"
- Probe whether the analogy is structural or surface-level. Surface ("they're both round") is weak; structural ("both have a central thing that everything else orbits because of an attractive force") is strong.
- Make the limits explicit: "Where does this analogy break? What does the original have that the analogy doesn't?"

**Examples.**
- An atom is like a solar system (Rutherford's model) — useful for orbital intuition, breaks when you hit quantum behaviour. Acknowledge both.
- The spread of an idea on a social network is like the spread of a virus — same structural dynamics (contact, transmission, immunity, R₀). Suddenly epidemiology becomes a tool for thinking about marketing.
- An engineering problem might map onto a biological one. If nature has solved a similar problem (bio-inspired design), the user has a head start.

**Watch for.** Cosmetic analogies. "The economy is like the weather" sounds deep but contains no structural mapping. Ask the user to specify which relationships carry over.

## Pattern Chunking & Schema Recognition

Develop the ability to see recurring patterns as wholes rather than separate pieces, by building mental schemas.

**Why it works.** Experts don't store more individual facts than novices — they store fewer, larger patterns. A chess master sees "kingside attack with bishop sacrifice" where a beginner sees fifteen pieces. Schemas massively extend what you can hold and reason about.

**How to apply with the user.**
- When they encounter a new situation in a domain, ask: "What category does this fall into? What's the type of problem this is?"
- Help them name the pattern. Naming is half of chunking.
- Build a small library deliberately: "Let's note this as a pattern. Next time you see it, you'll recognise the shape."

**Examples.**
- Math: a problem has "type" before it has details. Once recognised — "this is a related-rates problem" — the steps follow.
- Business: "this is a two-sided marketplace cold-start problem." "This is a commoditised middle." Naming the shape unlocks all the prior thinking that's been done about that shape.

**Watch for.** Forced pattern-matching when the situation is genuinely novel. A wrong schema is worse than no schema. If the analogy strains, drop it.

## Systems Archetypes (Common System Patterns)

Learn to spot the dynamic patterns that show up in many systems: feedback loops, exponential growth or decay, tipping points, self-organisation.

**Why it works.** Many systems — from economies to ecologies to personal habits — are not unique. They obey a handful of universal patterns. Recognising an archetype gives a ready-made understanding of how the pattern behaves and where it tends to lead.

**Key archetypes to keep handy.**
- **Reinforcing feedback loop.** Output amplifies input. Tends to exponential growth or runaway collapse. Examples: viral spread, compound interest, network effects, addiction.
- **Balancing feedback loop.** Output dampens input. Tends to equilibrium. Examples: thermostat, predator–prey populations, market price equilibrium.
- **Limits to growth.** Reinforcing loop runs into a constraint. S-curve. Examples: any startup's growth, biological populations, technology adoption.
- **Tragedy of the commons.** Individually rational behaviour produces collectively bad outcomes. Examples: overfishing, antibiotic resistance, attention economy.
- **Tipping points.** Slow buildup, then sudden state change. Examples: phase transitions, social revolutions, fashion shifts.
- **Delays.** Effects lag causes — gives oscillation. Examples: supply chains, economic policy, learning curves.

**How to apply with the user.**
- Ask: "Is there a feedback loop here? Where does an output become an input?"
- Ask: "Is there a limit this is heading toward?"
- Ask: "If everyone in this system did what's individually best, what happens to the whole?"

**Examples.**
- Topic: why a startup is no longer growing. Maybe it's hit the saturation phase of an S-curve. Maybe it's a feedback loop pushing in the wrong direction. Once you name the pattern, you can anticipate the outcome and intervene intelligently.
- Topic: why a relationship is deteriorating. Often a delayed feedback loop — the response to last month's grievance arrives this month, when the cause has been forgotten.

## Reference Class Reasoning

Ask: "What usually happens in cases like this?" — and base judgement on how similar situations have actually played out, not on how special this case feels.

**Why it works.** The brain treats every case as unique (it isn't) and over-weights vivid recent details. Looking at the base rate of outcomes — the reference class — corrects this. Daniel Kahneman called it the cure for the planning fallacy.

**How to apply with the user.**
- Ask: "What's the reference class? What is this an instance of?"
- Ask: "Of all the cases that fit that class, what fraction worked out the way you expect this one to?"
- If the user insists their case is special, ask: "Special how? What feature would actually move it out of the reference class?"

**Examples.**
- Estimating how long a project will take. The user thinks 3 months. Reference class: similar projects in this organisation have taken 6–9 months. The honest estimate is closer to 6.
- Predicting a startup's success. Founders feel 80% confident. The reference class of similarly-staged startups succeeds maybe 10% of the time.

**Watch for.** Picking too narrow a reference class so it conveniently contains only successes. Force a broader, more honest class.

## Distinguishing Signal from Noise

The other side of pattern recognition. The brain is so eager to find meaning that it sees patterns where there are none.

**Why it works.** Real pattern detection is probabilistic. Without skepticism, the user builds elaborate theories on what could be coincidence. Skepticism keeps the model accurate and saves mental energy.

**How to apply with the user.**
- Ask: "Is this a real signal, or could it be random?"
- Ask: "What's the sample size behind this pattern? Is it three anecdotes or thirty thousand observations?"
- Ask: "If this were just noise, how would we be able to tell?"
- Pause before letting them connect dots. "Is what you're calling a 'trend' actually statistically meaningful, or is it cherry-picked?"

**Examples.**
- A user has a theory based on three friends' experiences. Reference class is too small; theory is overfit.
- A market has moved up four days in a row. Pattern? Coincidence? The base rate of four-day runs in a random walk is high enough that this isn't evidence.

**Watch for.** Confirmation: the user remembers the cases that fit their pattern and forgets the cases that don't.

## How These Five Combine

In a real session: once the user has a structural map of the topic (Toolkit 1), pull in an analogy to make the structure intuitive. Test whether the analogy is real (structural mapping) or surface-level. Name the patterns/archetypes you find. Anchor the user's expectations to a reference class. And throughout, distinguish what's signal from what's narrative-fitting noise.
